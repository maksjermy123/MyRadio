# 📖 Оглавление + 📻 Радио + 📚 Глубже — Telegram Mini App

Христианский канал «От чтения к Преображению» как Telegram Mini App:
- Оглавление всех постов канала по категориям с поиском (в т.ч. по второстепенным тегам)
- Христианское радио (несколько станций, прямой эфир)
- Кнопка «📚 Глубже» в треде поста — библейские тексты, богословские цитаты, вопрос для размышления
- Проверка подписки на канал перед входом
- Автоматическая индексация новых постов через webhook
- Этот же бэкенд обслуживает и **второго**, независимого бота — [@mybible_reading_bot](https://github.com/maksjermy123/bible-reading-bot) («План чтения Библии»), подробности в разделе [«📖 План чтения Библии»](#-план-чтения-библии-второй-бот-в-этом-же-бэкенде) ниже

## Архитектура проекта

```
Telegram-канал (@Chtenie_Preobrazenie)
        │
        │  новый пост с #хэштегом
        ▼
Render (main.py — FastAPI)
        │
        ├── проверяет хэштег → определяет категорию
        ├── читает posts.json из кэша (TTL 45с) или с GitHub
        ├── добавляет пост → загружает обратно (фоновая задача)
        ├── запускает AI-анализ (Groq + Cohere + Bible DB)
        ├── сохраняет результат в links.json
        └── отправляет сообщение с кнопкой «Глубже» в тред поста (чат комментариев)
        │
        ▼
GitHub (posts.json + links.json — хранилище данных)
        │
        ▼
GitHub Pages (index.html + deeper.html — Mini App)
        │
        ▼
Пользователь открывает Mini App → Оглавление / Радио / Глубже
```

## Как работает кнопка «📚 Глубже»

1. Новый пост приходит через webhook — бэкенд отвечает Telegram мгновенно,
   сохранение и AI-обработка идут фоновыми задачами (дедупликация по message_id
   защищает от дублей при повторной доставке)
2. Бот индексирует его в `posts.json`
3. Запускается AI-анализ (Groq llama-3.3-70b):
   - Находит библейские тексты которые использует или которые дополняют автора
   - Cohere Rerank ищет релевантные богословские цитаты (порог 0.92 — если нет подходящих, не показывает ничего)
   - Формулирует вопрос для личного размышления
4. Результат сохраняется в `links.json` (retry на временные сбои GitHub API)
5. Бот отправляет сообщение с кнопкой «📚 Глубже» **в тред поста** (чат комментариев), не на сам пост канала
6. Пользователь нажимает «Комментировать» → видит кнопку первым сообщением треда → открывает `deeper.html?post_id=X` как Mini App

Кнопка **не добавляется** к постам с тегами: `#цитата`, `#анонс`, `#новости`, `#духовныйдневник`, `#юмор`, `#продолжение` (первая часть), `#без_глубже`.

### Алгоритм поиска треда для отправки кнопки

1. `getDiscussionMessage` — быстрый путь для новых постов (когда бот был admin при публикации)
2. Если 404 — `getChat(DISCUSSION_CHAT_ID)` → проверяет `pinned_message.forward_from_message_id`
3. Если pinned_message ещё не обновился — retry до 6 раз с паузой 10–60 сек
4. Если не удалось автоматически — добавить вручную через `/send_button?post_id=X&disc_id=Y`

**Как найти disc_id вручную:** зайди в тред поста → скопируй ссылку на первое сообщение (от «Telegram», `is_automatic_forward`) → число в конце ссылки `https://t.me/Chtenie_Preobrazenie_chat/XXX` и есть `disc_id`.

## Оптимизации производительности (актуальное состояние)

Все оптимизации функционально прозрачны — поведение то же, скорость выше.

### Бэкенд (main.py)
1. **TTL-кэш posts.json / links.json (45с)** в памяти процесса. `/links/{id}` больше не ходит в GitHub API на каждый клик (было 2 запроса + 300–800 мс). Запись инвалидирует кэш — свои изменения видны мгновенно.
2. **Мгновенный ответ вебхука.** Сохранение и AI-обработка — фоновые таски; Telegram не повторяет доставку по таймауту.
3. **JSON guard в analyze_post**: невалидный JSON от Groq не роняет обработку поста — одна повторная попытка.
4. **github_put: retry на 5xx** с backoff — результат AI-анализа не теряется при сбоях GitHub.
5. **DNS без блокировки event loop**: getaddrinfo в `_host_is_public` асинхронный — `/metadata` не тормозит остальные запросы.
6. **Явные параметры scheduler**: max_instances=1, misfire_grace_time=30, coalesce=True.

### Фронтенд (index.html)
- Все запросы к бэкенду через `fetchT()` с таймаутом — страница никогда не «виснет»
- Кэш оглавления в localStorage (`radio_toc_cache`) — мгновенный первый рендер
- Автоопределение темы (светлая/тёмная) из настроек Telegram

### Фронтенд (deeper.html)
- `fetchT` 15с + stale-while-revalidate кэш (`links_{postId}` в sessionStorage) — повторное открытие мгновенно
- Исправлена утечка обработчика скролла (`_scrollWired`)
- Сообщение об исчерпании ретраев вместо бесконечной загрузки
- HTML-экранирование данных (`esc()`)

## Первоначальная настройка (с нуля)

### Шаг 1 — Создать бота в Telegram

1. Открой **@BotFather** → `/newbot`
2. Придумай имя и username (должен заканчиваться на `bot`)
3. Сохрани токен вида `1234567890:AAG...`
4. `/mybots` → выбери бота → **Bot Settings → Group Privacy → Disable**
5. Добавь бота администратором в канал (права: «Управление сообщениями» + «Удаление сообщений»)
6. Добавь бота администратором в чат комментариев (те же права)

### Шаг 2 — Получить API ключи

- **Groq** (бесплатно): [console.groq.com](https://console.groq.com) → API Keys → Create
- **Cohere** (бесплатно): [dashboard.cohere.com](https://dashboard.cohere.com) → API Keys

### Шаг 3 — Создать GitHub Token

1. github.com → аватар → **Settings → Developer settings → Personal access tokens → Tokens (classic)**
2. **Generate new token** → название → срок **No expiration** → галочка ✅ `repo`
3. Сохрани токен `ghp_...` — показывается только один раз!

### Шаг 4 — Задеплоить бэкенд на Render

1. Зайди на **render.com** → **New Web Service**
2. Подключи репозиторий
3. Runtime: **Python 3**, Start Command: `uvicorn main:app --host 0.0.0.0 --port $PORT`
4. Вкладка **Environment** → добавь все переменные из таблицы выше
5. После деплоя скопируй URL вида `myradio-xxxx.onrender.com`

### Шаг 5 — Зарегистрировать webhook

```
https://myradio-xxxx.onrender.com/set_webhook
```
Должен увидеть `"ok": true`.

### Шаг 6 — Настроить кнопку меню бота

В **@BotFather**:
```
/mybots → выбери бота → Bot Settings → Menu Button → Configure menu button
URL:   https://t.me/preoradio_bot/radio
Текст: 📖 Оглавление + Радио
```

### Шаг 7 — Зарегистрировать два Mini App в BotFather

Бот использует два отдельных Mini App:

**Приложение `radio`** (Оглавление + Радио):
```
/mybots → бот → Bot Settings → Mini Apps → Add Mini App
Short name: radio
URL: https://maksjermy123.github.io/MyRadio/
```

**Приложение `deeper`** (страница «Глубже»):
```
/mybots → бот → Bot Settings → Mini Apps → Add Mini App
Short name: deeper
URL: https://maksjermy123.github.io/MyRadio/deeper.html
```

⚠️ Важно: URL для `deeper` должен указывать именно на `deeper.html`, иначе кнопка «Глубже» будет открывать оглавление вместо контента поста.

```
https://myradio-rrsk.onrender.com/cleanup
```

## 📖 План чтения Библии (второй бот в этом же бэкенде)

Этот же `main.py` на этом же Render-сервисе обслуживает **второго**, полностью независимого Telegram-бота — **@mybible_reading_bot** («План чтения Библии»). У него свой фронтенд (репозиторий [bible-reading-bot](https://github.com/maksjermy123/bible-reading-bot), свой `index.html`, задеплоенный отдельно на GitHub Pages), но бэкенд — один и тот же процесс FastAPI, что и радио/оглавление.

```
@mybible_reading_bot (Telegram)
        │
        ▼
Render (main.py — ТОТ ЖЕ процесс, что и радио)
        │
        ├── /plan/register, /plan/read, /plan/settings, /plan/unregister, ...
        ├── /state, /account/status  (полный снимок localStorage мини-аппа)
        └── cron раз в минуту → напоминания по notify_hour_msk/notify_minute_msk
        │
        ▼
Supabase (Postgres) — bible_accounts, plan_progress
        │
        ▼
GitHub Pages (bible-reading-bot/index.html) — сам мини-апп плана чтения
```

Виджет «План» в **этом** мини-аппе (Оглавление/Радио, вкладка «План», `renderPlanProgress()` в `index.html`) читает прогресс через `/plan/status?user_id=` — то есть один пользователь может открывать свой прогресс чтения из **двух разных ботов**.

### Переменные окружения для плана чтения

| Переменная | Значение | Описание |
|---|---|---|
| `BIBLE_BOT_TOKEN` | `1234567890:AAG...` | Токен **отдельного** бота @mybible_reading_bot (НЕ `BOT_TOKEN` — тот принадлежит радио-боту) |
| `BIBLE_PAGES_URL` | `https://maksjermy123.github.io/bible-reading-bot/` | Куда ведёт кнопка «Открыть план» |

### Таблицы в Supabase

**`plan_progress`** — одна строка на пару `(user_id, plan_id)`, то есть у одного человека может быть сколько угодно параллельных планов:

| Колонка | Назначение |
|---|---|
| `user_id`, `plan_id` | `UNIQUE (user_id, plan_id)` — **не** primary key на одном user_id, иначе второй план физически не создастся (реальный баг, словили и исправили) |
| `title` | Настоящее название плана (в т.ч. сгенерированное имя своего/хронологического плана) — самовосстанавливается на каждом открытии мини-аппа через `/plan/merge_days` |
| `streak`, `max_streak`, `last_read_date`, `days_done`, `start_date` | Канонический прогресс — единственный источник правды по стрику |
| `notify_hour_msk`, `notify_minute_msk`, `notify_on` | Время и включённость напоминания — своё для **каждого** плана отдельно |
| `last_reminder_sent_at` | Атомарная метка для защиты от дублирования напоминаний при нескольких воркерах (см. ниже) |

**`bible_accounts`** — одна строка на `user_id`, **никогда не удаляется** при `/users`:

| Колонка | Назначение |
|---|---|
| `reset_token` | Ротируется при полном удалении пользователя. Единственный способ клиенту узнать «меня сбрасывали с прошлого раза» — `plan_progress`/`app_state` после удаления просто пусты, и без этой метки клиент не может отличить «я новый пользователь» от «меня стёрли», см. `checkAccountReset()` во фронтенде |

`app_state` — третье хранилище, полный JSON-снимок `localStorage` мини-аппа (для синхронизации между устройствами), тоже хранится в Supabase, ключ — `user_id`.

### Эндпоинты плана чтения

Все, кроме `/plan/status`, требуют `init_data` (см. «Безопасность» ниже) — либо в теле POST-запроса, либо query-параметром для GET.

| URL | Метод | Описание |
|---|---|---|
| `/plan/register` | POST | Зарегистрировать план (или обновить title/время напоминания) |
| `/plan/status` | GET | Прогресс по одному плану ИЛИ сводка по всем планам пользователя. Единственный эндпоинт без проверки подписи — намеренно, вызывается кросс-ботово из виджета «План» в Оглавлении/Радио |
| `/plan/read` | POST | Отметить день прочитанным, пересчитать стрик |
| `/plan/unread` | POST | Снять отметку о прочтении (отмена) |
| `/plan/unregister` | POST | Удалить один план (не весь аккаунт) |
| `/plan/merge_days` | POST | Слить локальный и серверный `days_done` (не перезаписывает, объединяет). Тоже самовосстанавливает `title`, если сервер его не знал |
| `/plan/set_days` | POST | Явная перезапись `days_done` (редактирование своего плана) |
| `/plan/settings` | POST | Время/включённость напоминаний для конкретного плана |
| `/account/status` | GET | Отдаёт `reset_token` — клиент сверяет с локально сохранённым, чтобы понять, был ли полный сброс аккаунта |
| `/state` | GET / POST | Полный снимок `localStorage` мини-аппа — синхронизация между устройствами |

### Безопасность: проверка `initData`

`/plan/*` (кроме `/plan/status`), `/state`, `/account/status` проверяют, что запрос подписан именно ботом **@mybible_reading_bot** — тем же HMAC-механизмом (`verify_telegram_init_data`), что уже используется в `/verify` для радио-бота, только с `BIBLE_BOT_TOKEN` вместо `BOT_TOKEN`. Без этого любой, кто знает чужой Telegram ID (не секрет — виден в пересланных сообщениях), мог бы менять/удалять чужой прогресс через прямые запросы к API.

⚠️ **Важно при работе с этим кодом:** если когда-нибудь понадобится добавить проверку подписи к ещё одному эндпоинту — используйте `BIBLE_BOT_TOKEN`, а не `BOT_TOKEN`. Перепутать легко (уже наступали на эти грабли): `initData` подписан токеном ТОГО бота, через которого физически открыт конкретный Mini App, а не токеном "главного" бота проекта.

### Диплинки на конкретный план

Три разных механизма для трёх разных ситуаций — не взаимозаменяемы:

| Способ | Где используется | Как читается на клиенте |
|---|---|---|
| `?plan=<id>` в самом URL | Кнопка «Открыть план» в уведомлении-напоминании (`web_app` с прямым URL) | `new URLSearchParams(location.search).get('plan')` |
| `t.me/mybible_reading_bot/plan?startapp=open_<id>` | Построчные ссылки на каждый план в виджете «План» (кросс-бот, через `openTelegramLink`) | `tg.initDataUnsafe.start_param` |
| `t.me/mybible_reading_bot/plan?startapp=wipe` | Ручная принудительная очистка `localStorage` на конкретном устройстве (админский/отладочный сценарий) | тот же `start_param`, значение `wipe` |

### Напоминания: cron и защита от дублей

`bible_send_reminders()` — `@bible_scheduler.scheduled_job("cron", minute="*")`, раз в минуту запрашивает у Supabase, кому именно сейчас пора напомнить (`notify_hour_msk`/`notify_minute_msk` + `last_read_date != сегодня`), отдельно **для каждого плана**, а не для пользователя в целом.

APScheduler по умолчанию (`max_instances=1`) не даёт **одному** процессу запустить пересекающийся забег. Но если сервис когда-нибудь запустят с несколькими воркерами (`--workers N` в Procfile) — у каждого будет свой независимый планировщик, и без доп. защиты все они отправили бы одно и то же напоминание. Поэтому перед отправкой сервер атомарно "застолбливает" минуту через `last_reminder_sent_at` (условный `PATCH` в Supabase, а не проверка в памяти процесса) — работает и с одним воркером, и с несколькими.

Кнопка «Открыть план» в самом сообщении ведёт именно в **тот** план, о котором напоминание (через `?plan=` выше), а не в последний открытый — раньше оба напоминания при нескольких планах вели в одно и то же место.

### Онбординг-напоминания: побуждаем к первому шагу

Помимо ежедневных напоминаний по плану, cron отправляет два вида «мягких» напоминаний для тех, кто застрял на ранних этапах:

**1. План выбран, но 0 дней прочитано** (`days_done` пуст):

Приходит **каждый день в назначенное время** (как обычное напоминание), текст зависит от возраста плана:
| Возраст плана | Текст |
|---|---|
| День создания | Не приходит («ещё рано») |
| День 1 | 🌱 «План готов и ждёт тебя! Первый день — самый лёгкий...» |
| Дни 2–3 | 📖 «Ты выбрал план, но ещё не начал. Начни с малого...» |
| День 4+ | ⏳ «Ждёт тебя уже N дней. Просто открой один отрывок сегодня» |

После первого «Прочитал» переключается на обычный режим (стрик / отставание).

**2. «Старт» нажат, но плана нет вообще** (запись только в `bible_accounts`):

Цепочка максимум из **5 сообщений**: первое через **2 дня** после «Старта», затем каждые **3 дня**. Счётчик и метка последней отправки хранятся в `bible_accounts.onboarding_nudges` / `onboarding_last_at`; интервал считается от последнего напоминания (не от регистрации — иначе у давних регистрантов вся цепочка уходила бы подряд). Claim атомарный (условный PATCH), как у обычных напоминаний. После выбора плана цепочка прекращается автоматически; после 5 сообщений пользователь оставляется в покое.

⚠️ Перед деплоем требуется миграция Supabase:
```sql
ALTER TABLE bible_accounts
ADD COLUMN IF NOT EXISTS onboarding_nudges integer NOT NULL DEFAULT 0,
ADD COLUMN IF NOT EXISTS onboarding_last_at timestamptz;
```

## Технические детали

**Шрифты** — единая пара Inter + Source Serif 4 подключается через Google Fonts в обоих фронтендах. Для текста Писания в `deeper.html` дополнительно предусмотрен системный Georgia как fallback.

**Кнопка «Глубже»** — отправляется как сообщение в тред поста в чате комментариев с URL-кнопкой вида `https://t.me/preoradio_bot/deeper?startapp=POST_ID`. Telegram открывает её как Mini App внутри себя. `POST_ID` передаётся в `initDataUnsafe.start_param` на страницу `deeper.html`.

**Groq rate limit** — при ошибке 429 код автоматически ждёт 65 секунд и повторяет запрос (до 3 попыток). Если лимит исчерпан на весь день — ждать сброса в 03:00 по Москве.

**Ограничение размера файлов на GitHub Pages** — Fastly-CDN обрезает файлы больше ~900 KB без предупреждения (реальный инцидент: index.html 903 KB отдавался как 638 KB → тихо умирал JavaScript). Поэтому данные вынесены в отдельный `plans.json`/`posts.json`, а HTML держится компактным.

## Поддержание сервиса

**Render засыпает** на бесплатном тарифе через 15 минут без запросов. Решение — **UptimeRobot**:
- Мониторит `https://myradio-rrsk.onrender.com/` каждые 5 минут

**Groq лимит** — бесплатный тариф: ~6000 токенов в минуту. При анализе постов используй `delay=45`. Лимит сбрасывается каждые 24 часа (в 03:00 по Москве).

**GitHub Token** — без срока истечения. Если скомпрометирован — немедленно удали и создай новый. Никогда не публикуй в открытом коде.

**Логи Render** — при проблемах с индексацией ищи строки:
```
▶ update_id=XXXXX | поля: ['channel_post']
Пост 370 | теги: ['#библия'] | темы: ['📖 Библия и толкование']
Пост 370 — added ✓
✅ Post 370 processed. Related: [...]
✅ Кнопка «Глубже» → тред поста 370 (disc_id=XXXX)
```
